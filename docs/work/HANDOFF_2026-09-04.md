## 2. The landing machine (node1)

Scripts live in `~/.local/state/zclassic23/scratch/northstar/` (not in the
tree; copy them into `tools/` when you land the trains lane):

- `batch_build.sh <name> <worktree|branch>...` — cherry-picks lanes onto
  `origin/main` into `~/github/z23-stack<name>`; resolves generated-only
  conflicts (capability inventory, API reference, codebase map) itself.
- `stack_land_loop.sh <worktree> <name>` — rebase, `make lint-fast`,
  `dev proof ensure/wait`, push, under `proof.lock` (flock fd 9). One proof
  per box at a time. Run it as a systemd user unit
  (`systemd-run --user -p CPUQuota=1200% ...`).
- `relint_land.sh`, `stack_pick_lint_loop.sh` — full `make lint` under
  `prepush.lock` (fd 8) before a stack is offered to the lander.
- `glm_launch.sh`, `muse_launch.sh` — executor units; now pass
  `-p CPUQuota=800% -p Nice=12`.
- `z23_hourly_digest.sh` (timer `z23-front-page`, hourly at :07) posts the
  news front page to the board.
- `fleet_status.sh` — ASCII fleet table.

Measured limits that shaped everything:

- One proof = 15–45 min per box; the release LTO build inside it is ~20 min.
  `PROOF_TIMEOUT_MS` in `tools/dev/dev_proof.c` is 900000 (15 min) per
  child and is NOT tunable; under disk saturation the child exits 124 and
  the record says `child_proof_failed_exit_124`. Make it an env override
  (`ZCL_PROOF_TIMEOUT_MS`) as the first change you land.
- Every push to main restarts every in-flight proof (base moved). Land ONE
  batch per round; never run 20 lane loops against one lock.
- `ZCL_DEVLOOP_MAX_FILES=256` (`tools/dev/devloop.h`) refuses a changed set
  above 256 files with `changed_set_invalid_or_truncated`; filecap fixes it.
- `make lint` is 25 min cold, 2 min warm; `make lint-fast` is the push gate's
  first half.
- Node1 at load 450 was DISK-bound (431 blocked processes, NVMe 180 in
  flight), not CPU: 16 lanes building on one disk. Cap concurrent lanes on a
  box at about 4, and leave 8 cores for the qedc worker (owner rule).

## 4. The board (how agents talk today)

`~/.local/lib/z23/tools/board.sh post <kind> "<text>"` with kinds
`need|claim|result|problem|note|offer|directive`; a `ref` links a claim or
result to a need. Files are `~/.local/state/zclassic23/board/<host>.jsonl`,
synced between servers every 2 min (`z23-board-sync.timer`). The owner
never relays messages; an orchestrator must WATCH the board (node1 used a
45 s poll that wakes the session on any post from another host).

## 5. Plan: agents syncing faster, building together

The goal is one shared, typed, signed state that every agent reads and
writes, with a wake on every change, so no human relays and no agent
duplicates work. In order:

1. **One native channel.** Land node2's `zcode fleet say/read` and retire
   `board.sh` and the ssh sync. Transport is the P2P mesh over each node's
   onion, so the NAT'd laptop, Mac, and Windows members post and read the
   same board without any server account. Every post is Ed25519-signed by
   the node's identity; unsigned posts are refused.
2. **Typed posts, not prose.** Six kinds only: `need`, `claim`, `result`,
   `problem`, `offer`, `directive`. A `need` carries a task root (hash of
   the brief), the owning test groups, and the acceptance bar. A `claim`
   must reference a need; a `result` must reference a claim and carry the
   gate verdict with `groups_ran`; `groups_ran=0` is a typed `NOSHA` or
   `ERROR`, never `FAIL`. The board refuses a post that breaks the chain.
3. **Wake, do not poll.** `zcode fleet read --follow` streams new posts;
   every orchestrator runs it as a Monitor from session start. Agents
   subscribe to kinds and refs they own.
4. **One train per round, fleet-wide.** Landing is a replicated state
   machine: a node posts `claim train <base>` on the board, proves, pushes,
   posts `result train <new main>`. No other node starts a proof against a
   base another node has claimed. The `trains` lane (`z23-lane-trains`)
   automates this in the lander; land it early.
5. **Receipts that commute.** Per-group signed tickets in an MMR ledger
   (`z23-lane-sigreceipts`, `z23-lane-commute`): a group proven on any node
   against a base is accepted on every node while the intervening commits
   are disjoint from that group's files. This removes the "every push
   restarts every proof" wall and lets node3/node4 prove groups in parallel.
6. **Fast push gate, async release.** `z23-lane-pushgate`: the push gate
   proves a dev-profile build plus the owning groups; the 20-minute release
   LTO build runs after the push as `dev release qualify` and posts its
   ticket. A red qualify reverts by train, not by blocking every developer.
7. **Small units for small models.** GLM flash and Muse succeed on
   single-file test or leaf units with a fully specified interface and fail
   on multi-file work. `tools/engine_unit.c` (`z23-lane-glmharness`) is the
   harness: byte-ceilinged prompt, one group, typed error taxonomy, commit
   per PASS, Wilson intervals in `--stats`. Route flash there, never
   through an agentic CLI.
8. **Territories from the code index.** `z23-dev code tests <file>` already
   maps a file to its owning groups; add owner routing so a need names the
   node and executor tier that has the best pass rate for those groups
   (heuristics scored ONLY by gate outcomes).
9. **Per-box budget.** Every unit runs under a slice with `CPUQuota`,
   `Nice=12`, and at most 4 concurrent builders per disk; 8 cores stay
   free for qedc. `fleet bottlenecks` names the current constraint (disk,
   proof lock, or lint lock) so the dispatcher stops adding lanes to it.

Do these in that order; 1–4 need no consensus change and remove every
manual relay that happened this week.
