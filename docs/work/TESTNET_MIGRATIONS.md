# Configurable Z23 test networks and opt-in consensus migrations

Design for review against Z23 main at `7e4b79a01147736d564bbc545b8d1ca7fc2a99a2`. Command names, heights, thresholds and signal encoding below are proposals. No deployment has been scheduled.

## What a tester should be able to do

Start two nodes with an explicit test-network profile containing the Ironwood migration, fund a disposable wallet with mined test coins, signal for an upgrade, and observe the transition. Before activation, shield test coins into Sapling. After activation, create a shielded address, send to a second wallet using Ironwood, mine the transaction, restart the recipient, detect the note and spend it again. Also migrate a pre-activation Sapling balance. Record both peers' block hashes, transaction IDs and balances at each step.

## Isolate the network first

Use a generic profile selector, provisionally `z23 --testnet-profile=<manifest>`. Keep the existing testnet selector compatible. A profile may have a display label, but its canonical genesis configuration and initial consensus manifest identify the chain. There is no Ironwood-specific network type, flag, port convention, directory name or special case in the migration engine. A profile can exercise one migration, three together or different combinations over several heights. The same C23 binary can run multiple profiles in separate processes with independent stores.

A genesis profile fixes reproducible genesis bytes and hash, initial active migration IDs, protocol version, network and address domain parameters, replay protection, and a commitment to the initial deployment catalog. Separate profiles with incompatible genesis rules need distinct chain identities, peer discovery, datadirs, wallets and address domains. Agree on collision-checked network magic and transaction branch IDs before launch. Port numbers are configurable and do not establish chain identity. Never import spendable production state or keys. Record genesis reconstruction vectors and require a handshake mismatch test even if two profiles share a display name. Local rehearsal uses explicit peers, disposable keys and test-only funding.

Keep network selection, consent to follow a proposed fork, and miner signalling separate. The first chooses genesis and storage. The second authorizes a known transition on the node. The third expresses miner readiness. Nodes following the same profile and ancestry must derive the same rules. A node missing or declining a locked-in change stops at H−1 with a diagnostic. An operator who wishes to keep mining legacy rules selects an explicitly separate fork continuation with independent chainstate and peer routing. Old software may follow a legacy branch without understanding a proposal. Upgrading a binary does not itself schedule a deployment.

## Migration registry and deployment proposals

A migration is a versioned, reviewed C23 implementation. Give it a stable ID bound to its semantics and canonical conformance vectors; attest source/build identities separately. Declare prerequisites, incompatible migrations, affected validation and state domains, transaction format or signature-domain changes, and any forward/reverse state transformation. Register handlers explicitly in the binary. The profile selects compiled handlers by ID; mined bytes never supply executable code.

Compose independent checks as the conjunction of their predicates. If two migrations write the same consensus field, require an explicit ordering dependency with tested joint semantics or mark them incompatible. Sort the dependency graph topologically with stable ID tie-breaking. Reject cycles, duplicate IDs and unknown required dependencies before a node participates. Block H uses one atomic transition from a parent active set to a successor active set. Journal state edits and the active-set identity in the same block-connect transaction; disconnect restores the parent in reverse order. An interrupted transition must leave the old or new state complete. A data-format migration that cannot be undone needs a branch-scoped new store or a tested replay-from-checkpoint path before admission.

A proposal is deployment data. Its canonical hash binds genesis, the predecessor ruleset or eligibility conditions, the migration IDs requested, independent versus all-or-none activation, voting round, threshold, lock-in and activation height. Authenticate announcements through the existing signed release channel. Review and pin a round catalog before S. It maps compact vote slots to proposal IDs in canonical order. A profile can select a fixed-height activation for deterministic private testing or select miner-signalled activation. Both use the same resolver and ruleset registry. For later rounds, include catalog updates in an already agreed deployment or an explicitly accepted fork profile; a late announcement never changes a running window.

For an ordinary independent migration, use one proposal. For an inseparable combination, use one atomic proposal containing several migrations. At a given H, independently qualified proposals form a candidate set. A conflicting newcomer loses to a rule already active. In the remaining candidate set, mark both endpoints of every conflict simultaneously. Defer all marked proposals before pruning unsatisfied dependencies. Repeatedly remove proposals whose prerequisites are neither active nor surviving. Never add a removed proposal back during this round. Apply complete atomic bundles only. Normalize overlapping requests for an identical migration so it runs once. Specify resolution at proposal granularity for overlapping multi-migration bundles, with golden vectors, before enabling that feature. Record deferred reasons. Multiple compatible proposals crossing threshold together activate together regardless of miner ballot ordering.

Publish the new ruleset fingerprint computed from the genesis domain and the canonical active migration IDs and versions. Map each supported transaction-signing epoch on the profile to an unambiguous replay domain. Check the 32-bit wire branch IDs against other supported epochs and profiles; never assume truncating a ruleset hash makes a unique branch ID. Prepare interoperability and collision tests for every supported signing combination. Reject unsupported combinations explicitly. Broad combinations require a stable handler interface and dependency rules, not a separate named network implementation per combination.

## Miner signalling infrastructure

Proposed first wire format: one optional zero-value final coinbase output, single minimal OP_RETURN push of a four-byte tag, one format byte, a 32-byte round-catalog digest, and a fixed 32-byte ballot. One bit per proposal allows a miner to signal for any subset of up to 256 proposals per round. Slot zero uses the low bit of byte zero. Freeze literal tag, hash encoding, script and test vectors before launch. Unused bits must be zero. The bound limits on-chain ballot size per round; later rounds can introduce further migrations. The catalog defines individual thresholds. A block can contribute at most one vote per proposal. Only the designated final output is examined. A malformed, stale or unknown ballot contributes zero signals, subject to ordinary block validity. Silence is valid and counts in the window denominator.

Template generation inserts the selected ballot before computing the Merkle root and preserves subsidy, fees, height and extra nonce. Expose round digest, per-proposal slots, readiness state, and exact coinbase output in the template RPC. Pool software may preserve, replace or omit it, then recompute the Merkle root and mine that block. Full nodes count only accepted blocks on the candidate branch. Header-only observation requires the coinbase and a verified Merkle path. A miner preference or an unverified pitch never installs a rule or counts as a block.

## Deterministic switch at height H

For each round use one fixed window of W blocks from S through E inclusive, where E = S + W − 1. The manifest specifies S, W, integer threshold K, minimum lead time G and activation height H. Validate W > 0, 1 ≤ K ≤ W, G ≥ 1, and H ≥ E + 1 + G with checked height arithmetic. Count at most one vote per proposal per valid block on the candidate branch in the window. This measures blocks produced and is only an estimate of miner readiness. Ignore signals before S or after E. Keep protocol validity and voting separate.

| Height being validated | Rules and status determined from its parent |
|---|---|
| Below S | Parent rules, scheduled |
| S through E | Parent rules, signalling. Record this block's vote after validating it |
| E + 1 through H − 1 | Parent rules. Each proposal meeting its K through E is threshold-qualified on this branch; publish the deterministic resolution, conflicts and missing dependencies |
| H and later | At H apply the resolved compatible set atomically. If it is empty, retain the parent set. Expired and deferred proposals need an explicitly scheduled new round |

Illustrative local rehearsal: S=100, W=20, E=119, K=15, G=10, H=130. Fourteen votes leave the old rules in effect. Fifteen lock in after block 119, with ten full old-rule blocks from 120 through 129. Block 130 cannot vote itself active. Testnet operators choose public parameters after observing block cadence and upgrade lead times.

Derive the next-block rules from the **candidate's parent branch**, including during IBD. Cache the accepted block's tally and deployment state by block hash through the reducer and undo lifecycle. Fork choice compares accumulated work among branches valid for the selected ruleset. A reorg crossing E can remove lock-in; a reorg crossing H can reverse activation. Invalidate templates, mempool eligibility, note witnesses and wallet confirmations against the new parent. Restart, reindex, pruning and snapshot restore must reconstruct or authenticate equivalent state. A snapshot alone cannot establish missing signal history without a defined trust policy. Do not infer zero votes from a missing body or globally rewrite a height table while comparing competing branches.

## Pool policy at activation

A first profile can stage (A) v6 plus Ironwood, (B) the Sapling deposit freeze, and (C) an additional independent consensus migration. A profile intended for Sapling-to-Ironwood migration should require A for B, or put A and B in one atomic proposal. Wallet receiver selection is client policy tied to the active pool and user choice; it does not require a third consensus change. Pre-fund Sapling notes on this dedicated chain before activating B so withdrawal and migration are testable.

**Proposed deposit rule:** for each transaction accepted from H onward, require Sapling value balance ≥ 0, where the balance is Sapling spends minus Sapling outputs. Apply independently to every applicable transaction version, coinbase included, after normal range, proof and signature checks. A transaction without a Sapling bundle has zero Sapling balance. Per-transaction enforcement prevents one depositor from using another transaction's withdrawal in the same block. A coinbase must not create Sapling value after activation. Validate rewards under a separately specified coinbase destination rule.

| Movement at or after H | Expected result |
|---|---|
| Transparent or Ironwood value enters Sapling with negative Sapling balance | Reject |
| Existing Sapling note pays an Ironwood recipient and optionally returns Sapling change | Allow with a supported mixed-pool transaction, valid proofs and conservation |
| Existing Sapling note withdraws to transparent | Allow under the applicable transaction rules |
| Sapling spends and outputs balance exactly | Allow under the proposed net-deposit freeze |
| New default shielded receive address and wallet-selected shielded destination/change | Prefer an Ironwood receiver after activation. For explicit recipients with no eligible receiver, return a clear error |

The balance rule freezes net deposits. It cannot identify individual users' deposits inside an otherwise balanced private transfer. Forbidding every new Sapling output would also forbid ordinary Sapling change and would need a different proposal. Preserve scanning, balances, spending keys and witnesses for legacy Sapling notes. Give wallets an explicit migration operation with fee preview and confirmation. Do not silently migrate funds or reinterpret a Sapling address as Ironwood. Re-evaluate wallet defaults at the selected tip and validate mempool transactions for the next block, including expiry and reorgs.

## C23 implementation and verification sequence

- **Dedicated network profile.** Extend network selection, bootstrap, storage isolation and node status. Land the profile with readiness gating until it can actually validate Ironwood. Run existing mainnet, testnet and regtest goldens and explicit cross-network refusal tests.
- **Transaction and proof pipeline.** Implement strict v6 serialization and ZIP 229 digests using the existing C23 hash primitives. Pin the Z23 policy for pre-existing v4 transactions, v5 support and whether the distinct legacy Orchard pool is enabled. ZIP 229 presupposes v5 and Orchard on Zcash; neither is established on Z23. Cover mixed-version block authorizing-data commitments, the v6 anchor moves from effecting to authorizing data, and the correct per-pool txid/auth/sighash domains. Qualify the Orchard-protocol curve arithmetic, note encryption, key derivation, corrected Ironwood circuit, Halo2 verification and proving, spend authorization and binding signatures against pinned independent vectors. Implement separate Ironwood tree, anchors, nullifiers, pool balance and undo. Bind signatures to the designated testnet branch and reject invalid proofs before admitting effects. Keep cross-address and recovery rules aligned with the pinned specification. Parser-only fixtures cannot qualify a payment.
- **Activation and proposal infrastructure.** Add a pure C23 parent-state transition and signal codec with a test oracle. Integrate template production, externally supplied coinbase, block validation, reducer, chain index and replay. Existing height-only upgrade helpers need a parent-context route for conditional deployments. Cover all validation paths including fast sync and side chains. Add proposal/status RPCs exposing tip hash, votes counted, K/W, lock-in block, H, active ruleset, local opt-in and miner signal preference. Emit observable transitions only after the corresponding chain update commits.
- **Wallet and miner interfaces.** Wire construction, proving, fee estimation, address selection, shielding, deshielding, migration, trial decryption and balance display into normal commands. Test the transaction built by one process against a separate validating node and wallet; include fee, change, confirmations, restart and spend-back.
- **Qualification and optimization.** Exercise all eight subsets of three independent migrations, same-height dependencies, conflicting and overlapping proposals, atomic bundle rollback, staggered activation and unknown rules. Exercise K−1/K/K+1, marker absence and wrong IDs, both window boundaries, H−1/H/H+1, both opt-in settings, signal-free miners, competing branches with different lock-ins and reorgs across both boundaries. Compare restart, reindex and snapshot outcomes to a full replay. Verify pre-H Sapling deposits, post-H deposit rejection across block and mempool, post-H withdrawals, same-block deposit/withdrawal pairs, and rollback of both pools. Benchmark proving time, verification throughput, block-connect overhead, memory and wallet scan rate on identified hosts with identical workloads. Measure baseline and optimized C23 builds and retain independent cross-checks for every optimized path.
- **Delivery.** Use native claims, review and required sealed-core unseal/reseal and land gates for actual consensus changes. Publish the opt-in testnet instructions and binary identities after two-node qualification. Pushing reviewed code to main is distinct from activating it on any live chain. A future fork of an existing production chain requires its own network identity or an explicitly coordinated reference-compatible deployment, separate parameter decision, parity review and activation authorization.
