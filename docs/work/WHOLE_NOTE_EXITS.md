# Proposed whole-note legacy exits

This is a separate testnet design, not an amendment to the [net Sapling deposit freeze](SAPLING_DEPOSIT_UPGRADE.md). After its own activation, an eligible Sprout or Sapling note may be consumed only in a whole-note exit to transparent outputs or Ironwood, less the transaction fee. No legacy output may carry value, including change or an internal payment. This design is not implemented or qualified for activation; it requires a new consensus format, independent cryptographic review, a working wallet and the experiments below. Mainnet activation is outside this proposal.

## Transaction rules

Select one legacy source pool per exit. Require at least one real legacy spend, no transparent inputs, no spends from any other shielded pool, no value entering any legacy pool and no value-bearing output except transparent or Ironwood. Reject mixed source pools, coinbase, empty exits, unrelated value flows and any transaction format whose components cannot be classified. Existing spend proofs and nullifier checks establish ownership and prevent reuse; never disclose openings, plaintext, keys or values of input notes. An exit may spend multiple whole notes. Its recipient outputs plus fee equal the sum of those notes; the fee must be nonnegative and within existing monetary bounds. The sender chooses a destination and fee before signing; insufficient value, dust or an unavailable recipient must be reported without silently making legacy change. A transparent destination reveals the released value. Ironwood destination support is contingent on an independently specified and verified way to rule out real Ironwood spends despite any mandatory dummy actions; until then reject Ironwood exits rather than assume that an action count proves no spend.

For a Sapling exit require one or more Sapling spends, exactly zero Sapling output descriptions, and a positive Sapling value balance. Reject every Sapling output description, even one claimed to be zero: an encrypted output does not reveal its value. With no other input or legacy pool, the verified balance and ordinary conservation checks bind the entire spent value to eligible outputs and fee. Zero balance is not evidence of a whole-note exit. An exit whose entire value would become a fee is rejected: at least one eligible positive-value recipient is required. Transparent outputs can be checked directly; an Ironwood recipient requires a sound, specified proof of positive output value without exposing it, otherwise reject that route.

Sprout JoinSplits have two mandatory output commitments, so output count alone cannot express the same rule. Require each JoinSplit to have `vpub_old = 0` and both output commitments accompanied by distinct, canonical openings of zero-valued dummy notes. Recompute each commitment against its corresponding serialized output, reject any mismatch, missing opening or nonzero value, and preserve the existing JoinSplit proof, signature, anchor and nullifier checks. Require a positive aggregate `vpub_new` and an eligible positive-value recipient. Ordinary JoinSplit accounting and proof verification then constrain all consumed Sprout value to leave the pool; applying the rule to every JoinSplit prevents hidden intermediate change. Opening commitments proves their committed values only under the commitment's binding assumptions; it is not a substitute for proof verification.

The existing Sprout commitment function computes SHA-256 over the byte `b0`, a 32-byte `a_pk`, the eight-byte little-endian value, a 32-byte `rho` and a 32-byte `r`. The transaction carries commitments, not those openings. A testnet-only versioned transaction extension must encode exactly two `(a_pk, rho, r)` openings per JoinSplit, infer value zero, bind the openings and their order to the transaction's authenticated serialization and signature hash, and reject noncanonical lengths, duplicate openings and trailing data. Define its exact version, byte order, transaction-ID and signature-hash domains, size limits and parser behavior before implementation; an unauthenticated sidecar or mempool-only check is insufficient. Output-note randomness must be independently generated for each dummy; never reuse input-note material or publish input openings. The public dummy openings and transaction graph can reveal linkage metadata and do not provide receiver privacy. A new transaction version and compatible proof/signature construction are required; the existing format does not carry this witness. Check interoperability with the actual Sprout prover and independently verify binding and serialization before considering this feasible.

## Activation and reorganization

Give this design a separate testnet signaling identity and activation height, independently of the net-freeze proposal. Derive activation from each candidate block's parent branch. Enforce the complete rule on every transaction at and after activation, and retain historical validation before it. Block validation is authoritative; mempool admission and mining use the same next-block predicate, evict or reconsider transactions when the tip changes, and never treat a policy-only rejection as consensus enforcement. Revalidate proofs, witnesses, nullifiers, balances and signatures on replay and reorganizations crossing the activation boundary. Specify a network-specific signature domain and transaction version so a testnet exit cannot be replayed on another network. Do not reserve or claim a production activation height here.

## Qualification

Before any activation, construct and verify transactions on two isolated testnet peers with independently replayed pre-activation source notes. Record transaction bytes and IDs, source block and active parent, note values privately, fee, destination balance, wallet restart and rescan results, and block inclusion. Include a mature coinbase path under actual coinbase-protection rules; a rule that strands rewards is not ready. Exercise H−1, H and H+1, competing branches and reorganizations across the signaling window and activation, mempool eviction and reacceptance, double spends, and cross-network replay. Demonstrate construction and redemption, not just verification of an archived proof. Confirm complete block size and both peers' final balances.

Positive cases: one and multiple whole notes per legacy pool, multiple JoinSplits with two distinct zero dummy commitments each, transparent destination and fee, and Ironwood destination only after its no-spend and positive-recipient proofs are specified and implemented. Test minimum and maximum valid amounts and fees, restored wallets and restart. Negative cases: Sapling output descriptions including zero-valued outputs, partial exit with legacy change, legacy internal send, zero or negative Sapling balance, positive `vpub_old`, either nonzero Sprout dummy, swapped, omitted, malformed, duplicated or tampered openings, invalid JoinSplit proof or signature, duplicate nullifier, mixed pools or transparent inputs, unsupported versions, invalid fee, no positive recipient, and unauthorized Ironwood spend. Include transactions that net to an acceptable total while hiding a forbidden intermediate legacy output. Each rejection must be checked in block validation as well as mempool policy.

A commitment-component known-answer test can use 32 repeated bytes for each field: `a_pk=11`, `rho=22`, `r=33` gives zero-value commitment `9460dccaf2f2292fdaa24d67576d7b3cbd2efbfc2f658dbfa89f0877d590fac9`; value one gives `210bc07845a0f18d5e7fe0b688a5c5ad12d2b56f4cde85e684e071066cb18b59`. For a second distinct dummy, `a_pk=44`, `rho=55`, `r=66` gives zero-value commitment `d9f4ec0f762ecb4e042a93853f2c1da7f019536343759e3048cc664927642a9d`. These fixed bytes are test vectors, not production randomness, and do not establish a valid JoinSplit or prove end-to-end exit feasibility.
